# Multi-file batch redaction

We let users open several files at once as a **Batch**, but the Batch is only an orchestration layer over the existing single-`Document` pipeline: each file is opened, **Detected**, reviewed and **Redacted** independently and sequentially (one active `Document` at a time, `ReviewScreen` unchanged), then the redacted outputs are bundled for download together. We deliberately rejected a merged-corpus model that would dedupe **Items** across files — that would redefine Item/Occurrence to span Documents, complicate token numbering and locators, and surprisingly reveal to the user that a value also appears in another of their files. Keeping Documents independent preserves the Document seam and the per-kind rules (fail-closed PDF redaction).

## Consequences

- **Skip-and-continue, not abort.** A file that fails to open (e.g. encrypted PDF) or fails redaction (PDF verification leak) is quarantined out of the bundle; the rest of the Batch still produces output and the receipt lists what failed and why. Because PDF redaction is fail-closed per Document, skipping a failed file leaks nothing.
- **Mappings are packaged separately from redacted outputs.** Redacted files go in one bundle; **Mapping** sidecars go in a distinct bundle. Co-locating a redaction and its reversal key in a single artefact would undercut the redaction if that artefact leaked — so the obvious "one zip for everything" simplification is deliberately avoided. Whether a Mapping is produced is controlled by a global user preference in **Settings → Output** (off by default, persisted, no per-Document override on the review screen). When enabled, every successful **Redact** across all Document kinds — including **PDF** — emits a sidecar with the standard `Token → { category, value }` shape. For PDFs the tokens are assigned at redact time but are not written into the PDF bytes (the output is blanked glyphs); the sidecar records what was removed.
- **Lenient, gated intake.** A drop containing unsupported files (or exceeding the soft file-count cap) is accepted for the supported, in-cap files, but only after a warning modal enumerates what will be skipped and the user confirms (Continue / Cancel). When everything is supported and within the cap, intake proceeds with no interruption; when nothing is processable, it falls back to the existing dropzone error rather than the modal.
